# market-sim：数据脏乱时依然算得对的实时 P&L 管道

> **一句话**：一条端到端的实时数据管道，把行情流算成交易组合的盈亏（P&L）。数据会迟到、会重复、会损坏，还涉及多币种；在这种条件下，每一个数字都能对账、能追溯、能重算。

![架构图](architecture.svg)

## 1. 要解决的问题

交易台需要一张**近实时、可信**的盈亏表。现实中的数据源并不配合：

| 问题 | 在本项目里的样子 | 不处理的后果 |
|---|---|---|
| 迟到数据 | 约 3% 的消息事件时间早于之前已到的消息 | 持仓和成本按错误顺序计算，历史小时的估值错误 |
| 重复消息 | 同一笔成交被发送两次 | 持仓翻倍，盈亏虚高 |
| 坏数据 | 非 JSON、空价格、负价格、零成交量、未知标的、方向错误 | 管道崩溃，或更糟：脏数据悄悄混进报表 |
| 多币种 | EUR、USD、GBP、JPY；GBP 和 JPY 没有直接对欧元的汇率 | 汇总口径不一致，分不清"股票赚的"和"汇率赚的" |

数据源是我自己写的**确定性模拟器**：33 个标的（6 个交易所的 30 只股票 + 3 个汇率对），按真实交易时段和"跟着太阳走"的活跃度发消息。成交代表一个**做市台**自己的成交：赚买卖价差，每只股票有持仓上限，其中 10% 是"知情客户"的订单（成交后价格朝对方的方向走，也就是逆向选择）。所以 P&L 曲线有真实的业务含义，不是随机噪声。模拟器默认注入约 3% 的迟到消息和 1% 的坏行，重复消息可以按开关打开。同一个 seed 永远产生同一条流，所以任何问题都能复现。

## 2. 架构

管道采用 **medallion 分层（raw → clean → gold）**，全部放在一个 PostgreSQL 数据库的三个 schema 里：

1. **Ingest**（`ingest/ingest.py`）：通过 TCP 读取模拟器的 NDJSON 流，**原样**写入 `raw.events`。不解析、不去重；攒够 100 行或满 1 秒写一批。收到 SIGTERM 时先把手里的行写完再退出，退出前核对"收到的行数 = 库里的行数"。
2. **Raw 层**：只追加。`raw_id` 就是到达顺序，`payload` 用 text 保存，乱码行也照存。**上面任何一层都可以从这里重建。**
3. **Clean 层**（`clean.run()`）：解析、校验、去重。合格的行进入 `clean.trades` / `clean.prices`，不合格的行连同原因进入 `clean.dead_letter`。每次运行都记录对账结果。
4. **Gold 层**（`gold.run()`）：逐笔计算持仓和平均成本，生成按小时的估值快照、组合敞口与回撤、实时状态和预警，并为每一次历史修正留下审计记录。
5. **编排**（`pipeline/processor.py`）：一个常驻循环，每 5 秒依次执行 `clean.run()` → commit → `gold.run()` → commit；模拟时间进入新的一天时调用 `gold.nightly_fix()` 重算前一天。它只负责调度，**业务逻辑全部在 SQL 里**。
6. **服务层**：FastAPI（`api/main.py`）只读 gold，不做任何盈亏计算，SQL 参数走白名单；两个看板分别是实时 P&L（每 5 秒刷新）和数据质量。

## 3. 数据流：一行原始消息如何变成一个 P&L 数字

![数据流图](dataflow.svg)

### Clean：每一行都要有去处

- **增量窗口**：每次只处理 `raw_id` 落在 `(last_raw_id, max]` 区间的行。进度行用 `FOR UPDATE` 锁住，进度更新和数据写入在**同一个事务**里提交，所以不会漏处理，也不会重复处理。
- **校验顺序固定**：先查格式（JSON、type、id、日期），再查取值（价格、成交量、方向），最后查参照（标的是否存在、币种是否匹配）。**第一个不通过的检查就是这一行的原因**，一行只记一个原因，共 12 种。类型转换用 `pg_input_is_valid`，坏行不会让整批失败。
- **去重**：`clean.trades` 以 `trade_id` 为主键；`clean.prices` 以 `(instrument_id, event_time)` 为主键。同一时刻价格也相同，就是重复，直接丢弃；价格不同则是冲突，后到的那条进入 dead letter（`conflicting_price`）。
- **对账**：每次运行写一行 `clean.run_log`：
  ```
  raw 行数 = 坏行 + 好行
  好行     = 保留 + 冲突 + 重复
  ```
  每一项都**单独计数**，不是用减法凑出来的，所以等式本身就是一项检查。

### Gold：迟到的数据要落进正确的小时

- **持仓与成本**（`gold.position_state`）：逐笔使用平均成本法，支持空头，也支持一笔成交直接跨过 0（先平掉原持仓，剩余部分按成交价开新仓）。
- **迟到成交 → 局部重放**：如果新到成交的事件时间早于这个标的已经处理过的最晚时间，就删掉这个标的从该时刻起的状态，按 `(event_time, raw_id)` 顺序重放。只重放受影响的标的，不重算全表。
- **按小时的 as-of 快照**（`gold.stock_hourly`）：每个小时取"事件时间 ≤ 该小时"的最新持仓、最新报价和最新汇率。每个数字同时给出三种口径：本币、按当时市场汇率折算的欧元、按固定参考汇率折算的欧元。两种欧元口径的差额，就是汇率带来的盈亏。
- **汇率换算**（`gold.fx_rate_hourly`）：通过 USD 中转。`GBP→EUR = GBP/USD ÷ EUR/USD`，`JPY→EUR = 1 ÷ USD/JPY ÷ EUR/USD`。
- **组合层**（`gold.portfolio_hourly`）：已实现、未实现和总盈亏，多头、空头、总敞口和净敞口，历史最高点与回撤。
- **实时状态与预警**：`gold.live_state` 每个标的一行；`gold.alerts` 有 7 条规则，阈值按总敞口的百分比设置，**触发和解除用两个不同的阈值**，避免在阈值附近来回跳。
- **修正审计**（`gold.restatement`）：只要某个小时被重算后数字变了，就记下"哪个小时、什么原因（`late_trade` / `nightly_fix`）、改动前后的值"。

> **两个时钟**：`raw_id`（到达顺序）决定"处理到哪里"，`event_time`（事件时间）决定"算进哪个小时"。迟到数据因此不会被处理两次，也不会被算错位置。

## 4. 设计原则与保证

| 原则 | 实现方式 |
|---|---|
| 先落地，后判断 | Raw 层原样保存，规则改了可以整层重算（`sql/03_backfill.sql`、`sql/06_backfill_gold.sql`） |
| 不悄悄丢数据 | 坏行进 dead letter，原文一字不改，附带原因 |
| 幂等、可重跑 | 进度指针 + 主键去重 + `on conflict do nothing`；所有 SQL 文件都可以反复执行 |
| 每一步都对账 | ingest 核对行数；clean 用两层等式；gold 记录 run_log |
| 历史可以修正，但要留痕 | 迟到重放和收盘批处理都会写入 `gold.restatement` |
| 计算和展示分离 | API 只读 gold，不做任何计算 |

## 5. 怎么证明它是对的

- **模拟器测试**（`tests/test_market.py`）：消息格式、确定性、交易时段与周末、迟到/重复/坏行开关、价格合理性、波动率校准、日内活跃度曲线，以及做市策略的行为（赚价差、遵守持仓上限、知情订单让价格朝不利方向走）。
- **P&L 独立验算**（`tests/test_pnl.py`）：平均成本法用手算数字核对；另外用"总盈亏 = 现金流 + 持仓 × 最新价"从原始消息独立算一遍，再和结果比对。这个公式不依赖成本法。
- **SQL 集成测试**（`tests/test_pipeline_sql.py`）：建一个临时数据库，把 raw → clean → gold 完整跑一遍。输入里放了乱码行、负价格和一笔重复成交，断言对账结果是"10 行原始数据中 2 行坏行、1 条重复，balanced = true"；然后送进一笔迟到 20 分钟的成交，断言它触发了一次重放，11:00 这个小时的 P&L 被修正（100 → 200），并且写进了 `gold.restatement`。
- **运行时可观测**：数据质量看板展示拒绝率、拒绝原因、迟到分布和被修正的小时。

## 6. 取舍与扩展路径

**为什么用 PostgreSQL，而不是 Kafka + Spark？** 在单机数据量下，事务让"不漏、不重、对得平"非常容易证明，整套系统一条 `make up` 就能拉起。这个设计和流式架构是一一对应的：

| 本项目 | 生产规模的对应方案 |
|---|---|
| 模拟器 TCP 流 | Kafka / Event Hubs topic |
| `raw.events` | Bronze Delta 表 |
| `process_state.last_raw_id` | Structured Streaming checkpoint / Kafka offset |
| `clean.run()` 的去重与 dead letter | `dropDuplicates` + 隔离表 |
| 迟到成交局部重放 | watermark + 按标的 `MERGE` |
| `processor.py` | Airflow / Databricks Workflows |

**已知局限**：单节点；不建模夏令时；`nightly_fix` 只往回重算一天，迟到超过一天的数据需要手动回补；按标的重放和对全表开窗计算回撤，是数据量放大后最先需要优化的两处。
